Part 1 — LNC End Unit · STM32 Nucleo · C

1System context

The Local Node Controller (LNC) is one end unit inside the submarine. It carries the environmental sensors, watches the battery and the sonar, and reports to the Central Computer, which in turn answers to the Ground Station on shore.

The LNC never talks to the Ground Station directly. Its whole outside world is the Central Computer, reached through a single transport-independent link. Everything the LNC produces — keep-alives, events, data reports — flows up that one link; everything it obeys — configuration, RTC set, data requests — comes back down it.

2Execution model

The nine modules are logically concurrent: sampling runs every 5 s, keep-alive every 6 s, the sonar listens continuously, events arrive asynchronously, and the watchdog must be fed on time regardless of load. Two execution models can carry this; the module logic below is written to be independent of which you pick.

Recommended — FreeRTOS

tasks + queues

Each module becomes a task; inter-module traffic is FreeRTOS queues. The Communication send-priority (keep-alive > event > data) maps directly onto three queues drained in order, or task priorities. Periodic work uses vTaskDelayUntil; the sonar task blocks on its interrupt. This matches the spec's "modules exchanging messages" model almost one-to-one.

Alternative — super-loop + scheduler

cooperative, timer-driven

A cooperative scheduler runs periodic slots (5 s Monitor, 6 s Keep-Alive) off a timer tick; a single event ring-buffer is drained in main(); the sonar sets a flag from its EXTI/timer ISR. Lighter and fully deterministic, but you hand-manage timing and the priority queue yourself.

Design invariant

Modules communicate only through message queues + shared, mutex-guarded state (latest measurement, current mode, config). No module calls another's internals directly. This is what lets the same module code sit on either execution model — and it is what the "transport-independent" note in the spec is really asking for at the system level.

3Module map

Nine modules. Producers on top sense and decide; the two sinks — Event and Log — record and react; Communication is the one gateway to the Central Computer.

4Operating modes & the Event decision

The Monitor sets the mode by comparing each measurement to its limits. The overall mode is the worst of the four: Error if any value is in error, else Warning if any is in warning, else Normal. The Event module reacts only to transitions.

Limit shape — watch this

Temperature is a range (Normal min–max and Warning min–max) — both too-cold and too-hot matter. Humidity, light and battery are lower boundaries only: above the Normal floor is Normal, between the Warning and Normal floors is Warning, below the Warning floor is Error. Your comparison function must handle the two shapes differently.

Event module — actions by source

From Monitor (mode transition)

→Warning from Normal: LED yellow. From Error: LED yellow, stop alarm if active, resume full operation.

→Error: LED red, alarm on, button stops alarm, suppress non-essential ops.

→Normal: LED green; from Error also stop alarm & resume.

From Object Detection

Detected: LED red, alarm on, write events file, notify Central, button stops alarm.

Cleared: LED green, stop alarm if active, write events file, notify Central.

From Configuration

Write a timestamped line to the events file. No LED / alarm effect.

From Init

Write a startup line to the events file, recording whether the boot followed a watchdog reset.

Always

For every event, regardless of source, the Event module writes a timestamped record to the events file and sends a corresponding message to the Central Computer.

5Core data structures

Three shared records carry almost everything: the persisted configuration, a single measurement snapshot, and the event queued to the Event module. Keep them plain C structs so they serialize cleanly into TLV and into Flash.

/* ---- persisted in Flash; loaded (or defaulted) at boot ---- */
typedef struct {
    uint32_t magic;              // sentinel: distinguishes first boot from valid data
    /* temperature is a RANGE (both bounds) */
    int16_t  temp_norm_lo, temp_norm_hi;
    int16_t  temp_warn_lo, temp_warn_hi;
    /* the rest are LOWER boundaries only */
    uint16_t hum_norm_lo,  hum_warn_lo;
    uint16_t light_norm_lo, light_warn_lo;
    uint16_t batt_norm_lo, batt_warn_lo;   // ADC / potentiometer counts or mV
} lnc_config_t;

typedef enum { MODE_NORMAL = 0, MODE_WARNING, MODE_ERROR } lnc_mode_t;

/* ---- one sensor snapshot; shared "latest" copy is mutex-guarded ---- */
typedef struct {
    uint32_t  ts;          // RTC epoch seconds
    int16_t   temperature;
    uint16_t  humidity;
    uint16_t  light;
    uint16_t  battery;
    lnc_mode_t mode;        // worst-of the four
} measurement_t;

/* ---- queued to the Event module; timestamped on arrival ---- */
typedef enum { SRC_MONITOR, SRC_OBJECT, SRC_CONFIG, SRC_INIT } evt_src_t;
typedef struct {
    evt_src_t  src;
    uint32_t   ts;
    union {
        struct { lnc_mode_t from, to; measurement_t m; } transition;  // SRC_MONITOR
        struct { uint8_t detected; } object;                       // SRC_OBJECT (1=det,0=clear)
        struct { uint8_t after_wd_reset; } startup;                 // SRC_INIT
    } data;
} lnc_event_t;

6TLV message protocol

Every message on the wire is Tag–Length–Value. One byte of tag identifies the message; one length byte (extend to two if a value can exceed 255 bytes) gives the value size; the value is the payload. Messages can be nested — a keep-alive's value is itself a small run of TLVs.

Send order is strictly keep-alive → event → data, so status never starves behind a bulk data reply.

7Transport-independent communication

The spec's key constraint: UART today, Ethernet (or anything) tomorrow, with no change elsewhere. Achieve it with a function-pointer interface. The Communication module builds and parses TLV against this vtable and never names UART; only one small file implements it per transport.

typedef struct {
    int (*init)(void);
    int (*send)(const uint8_t *buf, size_t len);
    int (*recv)(uint8_t *buf, size_t cap, size_t *out_len);
} comm_transport_t;

/* one of these is selected at build/config time — nothing else changes */
extern const comm_transport_t uart_transport;
extern const comm_transport_t eth_transport;
Why it satisfies the spec

The physical transport becomes a single configuration detail behind three function pointers. Monitor, Event, Keep-Alive and the rest hand byte buffers to comm_send(); they can't tell UART from Ethernet, which is exactly the boundary the functional definition's NOTE demands.

8Persistence — Flash config & rolling logs

Configuration in Flash

The lnc_config_t struct lives in a reserved Flash sector, tagged with magic. At boot the Configuration module reads it; if the sentinel is missing (first boot) it loads compiled-in defaults and writes them back. Every accepted SET_* command re-persists and raises a config-changed event.

Rolling 7-day log

The Log module names each file by date and appends measurement lines. It keeps at most 7 files; on the 8th day it deletes the oldest before opening the new one. Needs a filesystem — FatFS on SD is the natural fit on Nucleo; a flash-backed file layer works if no card is present.

Decide early

The events file and the day-named log files imply a real filesystem. Confirm your board has an SD slot (or budget external flash + a file layer). This choice ripples into Log, Event, and the GET_DATA_RANGE / GET_EVENTS_RANGE replies.

10Central Computer & Ground Station

Out of the firmware scope but part of the system contract the LNC must satisfy.

Central Computer — 4 modules

Communication (LNC-facing): same TLV protocol, transport-swappable, a listener that routes received messages to the right module.

Management Command: builds & sends the SET_* / GET_* commands; handles responses.

Log: prints and persists logs to files.

Data Collection & Analysis: stores LNC data & events in a DB, produces reports by criteria. Keeps one week of data.

Ground Station

Requests, over Ethernet, the data the Central Computer holds for a given time window — both logged measurements and the events that occurred in that period. Read-only consumer of stored history.

13OOP mechanics to demonstrate

Inheritance

Common state/behaviour on Submarine; the two concrete types add only their own fields. No duplicated serial/name/inbox logic.

Polymorphism

Pure-virtual display() and updateMission() let the menu act on Submarine* uniformly. A virtual destructor is mandatory so delete through a base pointer runs the right cleanup.

Composition

CombatSubmarine has-a CentralComputer by value — created and destroyed with its owner, exactly the "belongs to" wording in the brief.

Association

Partners and message senders are references, not owners: CombatSubmarine* / Submarine* that point at fleet-owned objects. Never delete through these.

Encapsulation

Fields are protected/private; state changes (assign, end, message) go through methods that keep invariants — e.g. assigning a mission always flips availability.

Ownership

Prefer vector<unique_ptr<Submarine>> in the Fleet for single, clear ownership; keep raw pointers only as non-owning observers. Otherwise match every new with a delete and a virtual base destructor.

14Open questions to settle first

Four points in the brief are genuinely ambiguous. Resolve them with your instructor before coding — each changes a data structure or class relationship.

  1. Central Computer ownership. The brief says "each submarine has a central computer" but then "belongs to each combat submarine." This blueprint puts it on CombatSubmarine only (the explicit clause). Confirm it isn't meant for both types.
  2. "All the missions its fleet was managing." The requirement that a combat submarine track "all the missions that its fleet was managing" is worded loosely. Clarify whether that's a shared mission registry, or just the partners list for the current mission.
  3. Mission as a class vs. inline fields. Mission details differ by type. Decide whether Mission is its own class (cleaner for "assign / update / end") or the fields live directly on each subclass. The class model above keeps a thin Mission pointer for the available/assigned flag.
  4. Filesystem for logs. (Part 1) Day-named log files + events file need a filesystem — confirm SD/FatFS availability on your Nucleo, or plan an external-flash file layer.
